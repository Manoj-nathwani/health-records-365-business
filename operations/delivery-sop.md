# Delivery SOP

**Status: not yet written.**

## What this doc must answer

The stages, in order, each with an owner, an output and a measured duration:

1. **Intake** — see [intake and source mapping](./intake.md)
2. **Source mapping** — build the expected-source list for [the stewardship system](../product/stewardship-system.md)
3. **Requests** — see [the retrieval playbook](./retrieval-playbook.md)
4. **Chasing** — cadence, escalation, stopping rule
5. **Processing** — what happens to a document when it arrives
6. **Reconciliation** — building episodes, connecting events, preserving [uncertainty](../product/uncertainty.md)
7. **Open-item creation** — see [the open-loop lifecycle](../product/open-loops.md)
8. **QA** — see [the QA standard](./qa-standard.md)
9. **Handover** — delivering [the pack](./deliverable-spec.md)
10. **Ongoing maintenance** — the recurring cycle for product 2

## Why it blocks

Without a written SOP there is nothing to time, nothing to delegate and nothing to automate. It is the input to [the cost model](./cost-model.md) and the basis on which [the manual-first principle](../strategy/principles.md) eventually converts into software.

## How to write it

Write it *from* the customer-zero run, not before it. A SOP designed in advance will describe work that does not happen and miss work that does.
